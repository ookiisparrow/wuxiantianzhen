## 1. 端到端流程（一期）

```
直播（晚间）──抖店小黄车成交──订单带"款号"（商家编码）
        │
次日 8:30  运营从抖店导出订单+售后报表（含解压）→ 先处理退款
        │
上传 Web 后台 → 预检(Dry-Run) → 去重 → 同顾客合单成"订单包"
        │
9:00–13:00 整点优先派单（每人每次≤3单，1小时内确认）
        │   同款先问持有"余货"的织女
织女接单 → 扫线团条码核材料 → 队首订单包解锁图解 → 歌词式图解制作
        │
完工：扫"袋码"（封袋贴纸二维码）绑定订单包 → 拍成品照送审 → 运营审
        │
审过：装袋贴一次性封签再拍 → 选期望取件时段（仅提示）→ 提交
        │
Web 后台"待发货清单"（订单号 ↔ 织女工号 ↔ 抖店地址别名 ↔ 时段）
        │
运营在抖店 PC「在线寄件」（或已对接 ERP）按织女分批：切换发货地址→寄件并发货
        │
定期回导抖店订单/售后 CSV：运单号、退款、签收时间
        │
签收 → 7 天检视期 → 满 7 天入"待结款" → 每 14 天批量结款（手工银行转账）
```

## 2. 角色与权限

| 角色 | 入口 | 能做 | 不能做 |
|---|---|---|---|
| 织女 | 小程序（邀请制） | 接单、扫码、看图解、拍照、申领线材、看收入 | 看买家信息；跳单；下载图解 |
| 创作者 | 小程序 `creator` | 录入图解、预览（一期仅内部使用） | — |
| 志愿者审核员（阶段 1） | 织女端的审核入口 | 审照打分（看不到织女身份、有回避与校准） | 看织女身份 |
| 买家（小程序） | 买家端小程序 | 浏览、下单、微信支付、申请售后、客服消息 | 看织女身份 |
| 运营 | Web 后台 | 导单、派单干预、审照、待发货、结款、款式与图解上架 | — |

一账号多角色：`users.roles[]` + `tags[]`，不用互斥单角色。

## 3. 订单与派单

### 3.1 订单包
- 外部订单在入口统一转为内部**订单包**（`pkg_<id>`，`channel` + `externalOrderIds[]` + `tier` + 下单快照）。同一顾客在**派单前合单窗口**内的多笔订单合并为一包，整包只给一位织女，一个包裹一个袋码；开工后该顾客再下的订单成为新包。`定`
- 合单窗口：不要求严格 12 小时，由"晚间直播、次日 9:00 起派单"自然形成。合单键：`sha256(省|市|脱敏姓名|脱敏手机)`；窗口不重置；超单客工时上限自动拆新包。`定`（合单键是否可靠需看真实 CSV，见闸门 2）
- 交期：从付款起 14 天；第 12 天提醒；超期买家可继续等或全额退款，织女记一次超期。**超期责任（11-22 第 1 轮）**：一期熟悉的种子织女**不做判罚**；二期起超期的赔付由织女自行承担（是否排除不可抗力、如何扣款待协议阶段定）。`定`
- 单顾客工时上限：未寄出产品总工时 ≤ 一位标准织女 14 天可用工时的 70%。`定`（需每款标准工时）

### 3.2 派单
- 每天 **9:00–13:00 整点**派单，最晚 14:00 结束；不抢单、不设开放池。**一天一批**：8:30 导出时已付款的订单当天 9:00 起派，之后付款的顺延到次日。**限量上架**：开播前按织女剩余容量手工设抖店库存，卖完即止，系统给出"今日可售数量建议"（全体织女剩余容量之和）。`定`（11-22 第 1 轮）
- 每位织女每次最多 3 单，1 小时内确认；可一单都不接（不扣分，记回复率）。`定`
- 同一订单最多依次推给 5 位织女；放宽层级后次日 9:00 再取 5 位；仍无人或累计超 24 小时进"待处理"，由运营联系买家。`定`/`建议`
- **候选筛选**：先排除（接单开关关或休息日、容量满、色号不全、预计邮费超上限、**非固定款但未接受风险**）；再按层级（**持有同款余货** → 有现成品 → 回头客 → 同省 → 同大区 → 全国）；同层订单少时机会均等，订单多时叠加信用分。`定`
- 容量按工时：未寄出订单包工时之和 ≤ 织女 14 天可用工时的 70%；并且预计能在第 12 天前做完才派。`定`
- 拒绝与超时不扣信用分，记回复率；连续 3 次超时暂停派单 7 天；被取消/超期比例超阈值暂停。`定`（阈值待定）
- 织女订单队列：按接受顺序固定排队不可调整；队首才看图解；约取件成功后下一包成队首；队首卡住由运营放行或改派。`定`

### 3.3 取消与退款（无定金）
| 阶段 | 规则 |
|---|---|
| 派单前（合单窗口内） | 买家取消 → 订单出队，`cancelled_full` |
| 派单后、接单前 | 同上 |
| 开工后取消（固定款） | 织女继续做完，登记为**余货**；下一次同款订单优先派给她，只需换新订单的袋码贴纸、重拍封签照；工价按新订单结，不另补偿。**平台不回购、不补贴**；平台设计**定期统一处理余货的机制**：每场直播优先清被取消的成品，仍有冗余则定期（每月或每周）开"成品专场"，只卖成品；**该款只要仍有余货，就不再放新的订单**（具体形式与规则待第 2 轮）。`定`（11-22 第 1 轮） |
| 开工后取消（非固定款，二期） | 走兜底，见 §6 |
| 已约取件之后 | 买家不能取消，只能签收后按退货处理 |
| 签收后 7 天内 | 未拆封、封签完好可退货退款，运费买家出；已拆封不支持无理由；质量问题凭照片联系客服 |
| 签收后质量问题（11-22 第 1 轮） | 退货邮费由平台承担；**平台从订单中抽取一部分作为"运营资金池"**；经核实为**中等及严重**质量问题的，产品退还给织女；仅**轻微**质量问题的，进入平台统一退货区域，尝试二次销售。退款金额谁承担、质量分级标准与判定人待第 2 轮 |

抖店无理由退货与定制商品的规则边界尚待律师确认，不得对外承诺"定金不退"。

## 4. 织女流程与小程序（一期）

### 4.1 线性工作流 `定`
接单（含 1 小时内扫线团条码核对本包所需色号）→ 轮到队首解锁图解 → 制作（歌词式界面）→ 扫**袋码**绑定订单包 → 拍成品照送审 → 审核放行 → 装袋贴封签再拍 → 选期望取件时段并提交 → 进入待发货清单。服务端检查前置步骤，按钮灰着不算数。

### 4.2 袋码与封签 `定`
- **袋码** = 封袋贴纸上的唯一二维码，订单包级，一包一码，不绑实物。平台定做，**批量寄给织女、用完在小程序申领**；状态 `unused → bound → void`；余货复用时旧贴纸作废、换新；织女未使用数低于阈值时提示申领。
- **封签** = 一次性防拆封签，与袋码分开两张（推荐，`建议`）。织女装袋拍照留底；退货时平台验封签。
- 扫描：袋码已使用或属于别人 → 拒绝。
- **术语约定**：**款号**（`skuCode`，抖店商家编码，款级）与**袋码**（`bagQrCode`，订单包级）分开，全文不使用"件码"。

### 4.3 其他
- 买家地址对织女不可见；运营才操作抖店；织女只看到收件省市（用于同省优先派单与邮费估算）。`定`
- 图解：队首才可看；全屏织女工号水印；私有云存储短时效链接；订单结束失效；开启微信截屏/录屏保护；仅在小程序内查看不可下载。`定`
- 通知：每天 8:50 服务号或短信提醒"今日 9:00 起派单"；整点有新单以小程序内提醒为主、短信为辅；订阅消息一次授权只发一条，不能单独承担。`建议`
- 织女可随时关闭接单开关（不扣分）、设休息日。`定`
- 收入页：待结算、已结算、每一件的明细（售价、各项扣费、邮费分担、实得）。`建议`
- 取件时段：织女选"方便上门时段"，**仅作为给运营的提示，不保证**（抖店在线寄件未确认可指定时段）。`定`

## 5. 材料与个人线材预算池 `定`（终版，2026-11-23 更新）

- **12 基础色、标准辅料套件化与江浙沪供应商圆心策略（2026-11-24 更新）**：
  - **江浙沪供应商圆心 + 分大区阶段扩展**：主供应商选在**江浙沪毛线与手作辅料产业带**；全国划分为业务大区（**江浙沪核心区、北方区域、云贵川西南区域、西北方向、华南华中**等），**前期优先招募与准入以江浙沪供应商为圆心的织女**，实现材料寄送 1–2 日极速达、最低首重邮费与高密度上门取件覆盖；后续随规模按阶段逐个解锁大区。
  - **12 基础色与辅料套件化同仓代发**：织女入驻自备 12 色基础包（主供应商上架专属链接），并让主供应商将指定规格 PP 填充棉、安全眼、钥匙扣件、胶水打包成**标准辅料包 SKU**，随毛线一起在小程序线材池申领代发，从源头统一毛线与非毛线辅料品质。另测样保留 1 家同品牌备选店防断货。
- **线材供应路径（2026-11-23 更新，取代"手工去平台逐单代下单"）**：采用**直连指定供应商的表格一件代发**——跳过 C 端平台逐单下单（避免防代拍风控与手工复制地址人力），平台不囤货：
  1. **每周截单导表**：每周固定截单日，运营后台按**商家打单软件导入模板**（收件人、手机、省市区、详细地址、供应商官方标准色号编码、数量、备注）一键导出单张申领 CSV；系统严格使用供应商官方色号编码，不使用口语颜色名。
  2. **发单与结算**：运营将汇总表发给主供应商，由商家直接导入打单软件出单直发织女；前期**先款后货**，核对总价后按批结算（微信/支付宝按批转账，或走 1688 改总价拍汇总单以留存官方交易/入账凭证）；商家回传含运单号的回执表（可选回导）。
  3. **规模化演进**：单量放大后，在后台开放极简供应商端账号或对接对方 ERP API（聚水潭/旺店通等）。
- **个人线材预算池，严禁透支**：材料费（`EXP_MATERIAL_COST`）单独计入商品售价，签收满 7 天结款计提时全额划入织女线材池（**不从织女纯劳动工价中倒扣**）；**12 基础色仅入驻第一套自备，后续用完后照样可在小程序线材池申领补货**；每周申领时通过 `weaverAccounts` 原子余额锁严格校验 `池内余额 ≥ 线材成本 + 实际低价邮费` 后扣减（`yarn_out`）。提前与供应商锁定**非偏远首重/续重价及偏远地区加价表**，直接配入系统扣费逻辑；**起领门槛（2026-11-24 定）**：满 **3 团**起发，或直接按“单款补色材料包”整包申领，以控制邮费占比。新人先接 12 基础色订单攒额度，平台零垫资。
- **单品线材克重 BOM、估算余线台账与不亏空定价（2026-11-24 定）**：
  1. **克重 BOM 与自动算材料费**：每团线材在 `yarnCatalog` 录入标准克重（`unitWeightG`）与单价（`unitCostFen`）；每个款式在 `styles` 录入各色号实测净重（`yarnBom`）及损耗冗余系数（默认 10%，应对手劲松紧与接线头），系统向上取整自动算出单件耗线克重与材料费（`materialCostFen`）。
  2. **计入售价、保证线材池不亏空**：单件材料费直接计入产品定价成本，并作为 `yarnPoolAccrualFen`（不低于 `materialCostFen`，可叠加少量补线邮费缓冲）在每单结款时精准划入该织女的个人线材预算池，确保线材池账面收支平衡不亏空。
  3. **织女“整团 + 克重”双颗粒度余线台账（2026-11-24 细化）**：取代原只有“有/无”的 `extraColors[]`，为每个色号同时记录 **`wholeSkeins`（完整线团数，通常 50g/团）** 与 **`usedSinceCheckG`（自上次核对以来累计消耗克重）**：
     - 入驻 12 基础色或小程序领线确认收货时，直接按**整团数**入账（如 5 团）；
     - 织女每做一单，系统按 BOM 克重累加 `usedSinceCheckG`；**每累计满 1 团（如 50g）**，小程序主动弹出 1 秒快捷核对：“某色线预计已用掉 1 团，请问你手头完整线团还剩几团？”织女点一下实际团数（如 4 团或 3 团），系统立刻以真实整团数校准（确保至少还有 `N × 50g` 可用）并重新从 0 累计，**将估算误差永远锁死在单团（50g）以内、绝不滚雪球**；
     - 当累计消耗接近全部团数（如 5 团 250g 即将见底）时，主动核对“是否几乎用完”并支持一键加入本周补线申领。
- **签收点亮解耦与色号掌控（2026-11-24 第 8 轮修正）**：现实中毛线团**没有可识别色号的条码**，原“扫线团条码核材料/收货”作废。改由**织女必须在小程序内申领线材**使系统精准掌握每位织女拥有的色号与估算克重；运营每周截单导表发给主供应商后一键标为 `dispatched`（不再强制回导几百条运单号，单号表留微信备查）；织女收货后在小程序**点击确认收货（可选拍到货合照）**即自动累加对应色号克重并解锁对应新款派单；日常接单时无需扫码，成品照审核兜底色差。
- 每周补色邮费暂定从池内扣；织女彻底退出时池内未用余额随最后一次 14 天结款退还。
- 第一批主推款**只用 12 基础色**破冰（`建议`）。

## 6. 固定款与非固定款 `定`

| | 固定款 `core`（一期仅此类） | 非固定款 `trial`（二期） |
|---|---|---|
| 定义 | 直播间主推的个位数稳定款 | 测款、小众款 |
| 谁能接 | 所有织女 | 仅 `acceptsTrial=true` 的织女；其他织女看不到入口 |
| 开工后取消 | 继续做完成余货，同款优先复用，不另补偿 | 见下兜底 |
| 风险 | 低 | 取消后无法售出，**不可消除** |

**非固定款兜底（已采纳）**：①织女自愿接受风险（字段 `acceptsTrial`）；②成团制（同款累计 N 单才派单）；③订单卡明确标注"测款，开工后取消有风险"；④工价含风险溢价；⑤开工后取消仅有限补偿已用线材成本（或封顶进度补偿，流水 `trial_comp`）；⑥余货由织女自留，或平台按材料成本买断后做福利款/清货；⑦仅对完成率与品控稳定的织女开放。**待定**：成团数 N、溢价比例、补偿封顶、样品补贴额度。

## 7. 物流与发货

### 7.1 通道一 `douyin_online`（一期，抖店订单）`定`
- 不接抖店开放平台 API 与快递 API；Web 后台导入抖店 CSV；织女完工进入**待发货清单**（订单号可一键复制 + 织女工号对应的抖店地址别名 + 期望时段）；运营在抖店 PC「订单发货 → 发货中心 → 在线寄件」按织女分批：筛选该织女订单 → 切换到她的发货地址 → 点"寄件并发货"；定期回导订单/售后 CSV 更新运单号、退款与签收。
- 系统**不存买家明文地址**，只存省市（同省优先派单用）。
- 抖店在线寄件要点（官方）：7 家物流商（中通、极兔、圆通、申通、韵达、京东、顺丰）；首重最低 3 元；17 点前发起可当日上门；不占自行寄件额度；不需要自有面单账号/月结；运费从货款账户或抖店钱包扣；0–30 kg；**只支持本店订单，不能手填收件人**；**无 API**；发货城市须在开通名单内。

### 11.4 订单包状态机 `ORDER_PACKAGE_STATUS_SPEC`
`confirming`（派单前合单窗口）→ `waiting_dispatch` → `offered`（1h 接单）→ `making` → `photo_review`（驳回回 `making`）→ `awaiting_seal` → `ready_to_ship`（进待发货清单）→ `shipped` → `signed`（7 天检视）→ `settled_ready`（终态）。异常/终态：`manual_hold`（5 次不接、卡单、超期）、`cancelled_full`（接单前取消）、`cancelled_made`（开工后取消：固定款→余货；非固定款→二期兜底）、`returned`（签收后退货）。

### 11.5 不可变账本
确定性幂等键：`craft:${pkgId}`、`ship_reimb:${pkgId}`、`trial_comp:${pkgId}`（二期）、`yarn_in:${pkgId}`、`yarn_out:${claimId}`、`royalty:${pkgId}:${creatorId}`、`payout:${batchId}:${payeeId}`。线材池不可透支校验：先写 `claim_${weaverId}_${weekKey}` 占坑 → 聚合该织女 `yarn_pool` 流水余额 → 严格校验 `balanceFen ≥ materialsCostFen + shippingFeeFen`，不足删占坑拒绝，足够写负流水。
后期扩展（博主分佣、退货再售补款、保证金扣减、补助池）直接追加 `entryType`，不写死扣费列。

### 11.6 抖店 CSV 增量导入规范
- 编码：前端读 `ArrayBuffer`，先 `TextDecoder('utf-8',{fatal:true})`，失败降级 `gb18030`，去 BOM、引号、制表符；官方导出为**加密压缩包**，解压密码发到验证手机/邮箱，导入页提示"先解压"。
- 解析：PapaParse 按中文表头；拦截科学计数法订单号（`/e\+/i`）与未知 `skuCode`；先 `previewDoudianCsv` 展示新增/更新/报错汇总，无阻断错误才允许提交。
- 去重与合单：先查 `externalOrderIndex`；新单按合单键找 `confirming` 且 `now < dispatchableAt` 的包合并；旧单绝不重建，只按最新信号驱动 `transition()`。
- 状态回导：接单前整包退款 → `cancelled_full`；接单后整包退款 → `cancelled_made`；合单部分退件高亮提醒运营；出现运单号 → `shipped`；出现签收/完成时间 → `signed` 且 `settleEligibleAt = signedAt + 7d`。
- 每日节奏：约 8:30 重新导出订单与售后 CSV（先处理退款）→ 9:00 起整点派单。
- 商家编码写入规则：款号写入商品/SKU"商家编码"；有色卡的 SKU 建议 `款号-色号`；末端对应表以**订单号**为键，款号只用来查产品参数。

| 付款通道 | `config.payoutChannel`；`ledger.payout` 流水不绑定具体通道 | 一期手工转账 → 灵活用工或代发平台 |
| 审照可跳过 | `orderPackages.reviewMode`（`required`/`sampled`/`skip`）；状态机里 `photo_review` 按规则可跳过，一期全部 `required` | 规模化后审照成为瓶颈 |
| 买家信息收口 | 所有读写买家字段（密文、省市、合单键）集中在一个模块 | 三期若要解密，需拆成"抖店网关"部署到抖店云 |
| 渠道无关 | 订单包不含抖店特有字段；渠道差异只在导入器 | 抖店规则变化/封店，二期接小程序或另一渠道 |
| 线材供应商 | `yarnCatalog.supplierId`/`supplierSkuCode`；`yarnClaims` 支持按打单模板导出 CSV 与确认收货 | 一期表格一件代发，规模大后切供应商端账号或 ERP API |
| 多款订单 | 订单包保持 `items[]`；常买组合建独立套装款号 | 避免拆单；真要拆单时有接缝 |
| 经营主体 | 主体信息放配置，不写死；AppID 注册前先确认主体 | 二期前可能另设公司，AppID/云环境难迁移 |
| 知识产权 | 款式与图解保留 `ownerType`（`platform`/`creator`）、`licenseDocId` | 外部创作者二期进来时权属清楚 |

**一期不做**：区域点、团队账号、灵活用工接入、自动抽检、多渠道导入、抖店网关、供应商对接、创作者权属管理的任何功能。

### 两池架构（用户 11-22 澄清，取代"500+ 织女都接抖店订单"的假设）

> 用户原话：直播间的供给织女 500 个就够了，新增的织女不需要供给直播间订单，只需要在微信小程序上能处理就可以。

| | **直播池** | **小程序池** |
|---|---|---|
| 人数 | 最多约 500（正好是抖店发货地址库上限） | 无上限 |
| 订单来源 | 抖店直播间订单 | 微信小程序订单（买家下单、微信支付） |
| 寄件 | 抖店在线寄件，或开放平台电子面单 API；织女地址登记在抖店地址库 | 不走抖店，不受 500 上限约束；候选：快递100 上门取件（线上预充，平台付运费） |
| 需求侧 | 直播销量 | 老玩家复购、测新款、私域社群；三期 B 端与博主代钩单 |
| 管理难点 | 500 个席位的进入与退出；地址库增删；订单量大时手工在线寄件不可持续 | 需求来源与上线时点；微信支付、类目与主体资质；买家地址落库的个人信息合规；二清与退货规则 |

**这个澄清带来的变化**
1. 抖店 500 地址上限不再是障碍，而是直播池的容量；"主轨道"问题变成"直播池如何自动化"与"小程序池如何尽快上线"两件事。
2. "无上限织女"的"无上限"落在小程序池，所以**小程序池的订单需求**成为新的关键问题；原计划放二期的"买家小程序下单 + 微信支付 + 快递100"，现在是无上限织女的收入来源，需要重新评估上线时点。
3. 11-21 废弃的"小程序商城 + 微信支付"回到了设计里，要和二清、退货、类目资质、抖音引流合规一起重新看（这些仍待律师确认）。
4. 直播池的席位需要管理：按什么进入、退出、是否可从小程序池晋升。

**直播池的自动化仍是问题**：一场直播的订单分散到上百位织女，在线寄件要先切地址再勾选，手工操作会是"每位织女一批"，几百批每天不可持续（推断，取决于日订单量）。API 路径（订单 API + 电子面单 API）需要软著与主体一致，个体户资格未明；500 上限与直播池恰好吻合，所以 API 路径的上限问题基本不再是障碍。

**其余组件（审照、付款、准入、线材、客服）的规模化候选路径**仍见上一版落差表的内容，并分别应用于两池，详见第 3 轮问卷。

**一期的重新定义（待第 3 轮确认）**：3–5 位手工织女只作"履约质量验证"，可与规模化版本的开发并行；一期架构必须是规模化架构。

## 15. 两池与规模化设计决定（2026-11-22 第 3 轮）

### 15.1 两池
- `users.pool`：`live`（直播池）或 `mp`（小程序池）；`users.poolRank`、`users.cityQuotaKey`；席位按"表现动态排名（按月或季调整）+ 城市配额"混合管理；表现好的小程序池织女补位，直播池连续低于线的退回小程序池。
- 订单包 `channel`：`douyin_online`（抖店）或 `mp_wechat`（小程序）；**派单候选必须属于该渠道对应的池**：抖店订单只派直播池，小程序订单派给小程序池（也可派给直播池织女，待定）；小程序池织女不接抖店订单（不溢出）。
- 直播池织女的发货地址登记在抖店地址库（≤500）；小程序池织女的地址不入抖店，只入 `addresses`（二期占位 → 阶段 1 启用，仅云函数可读）。

### 15.2 小程序池交易
- 平台自营（主体是卖方）+ 织女受托加工，与直播池同一套结算；织女看不到买家信息。
- 新增：买家小程序、商品与库存、微信支付（`payments` 集合与收款账户流水）、退款、订单与售后；寄件走快递100 上门取件（线上预充，平台付运费），运单号回调自动绑定。
- 待律师：二清、退货规则、类目资质、从抖音引流到微信的合规；主体与支付资质（决定是否注册公司）。

### 15.3 直播池自动化
验证期 ERP 过渡；同时立即启动软著与开发者资质；就绪后切开放平台 API：订单 API 自动拉取、电子面单 API 取号、织女地址登记为网点。前提：个体户能否做开发者（工单）。

### 15.4 共同能力
- **分级实名**：`users.verifyLevel`：`phone`（接单前，手机号 + 微信）→ `payee`（首次结款前，实名 + 银行卡）→ `full`（月收入达税务门槛）。
- **质检**：`orderPackages.reviewMode`：新织女、新款 `required`；稳定后 `sampled`，比例随信用分动态下降；同步实现**志愿者审核**（志愿者看不到织女身份、有回避与校准，见 §9；激励形式与法律 L11 待定）。
- **线材**：少数主供应商深度合作，统一色号与批次、对账、价格协议；`yarnCatalog.supplierId`；供应商直发给织女，平台从线材池结算。
- **客服与异常**：买家走抖店客服；织女走小程序内工单 + 社群；卡单、超期、改派由规则自动处理。

## 16. 开发前结构性决定（2026-11-22 第 5 轮）

- **两个小程序**：买家端（电商类目，微信支付）与织女端（工具类目，含图解、审照、线材、结款）；共用同一云环境与数据库；以 `users.role` 区分身份，两端各自的 AppID 在主体确定后再注册。
- **跨池派单**：订单包 `channel` 决定候选池：抖店订单只派 `pool=live`；小程序订单先派 `pool=mp`，直播池织女作为低优先级候选；`pool=mp` 的织女永不接抖店订单。
- **订单粒度**：`orders` 与 `orderPackages` 保持一对多的结构；小程序首版不开放一单多款（套装用独立款号），抖店订单待真实 CSV 样本验证后再放开。
- **通知**：订阅消息为主；派单后确认时限的最后 10 分钟补一条短信；`notifications` 记录授权状态与触达结果，供改派统计。**待核实**：订阅消息的授权与额度规则、短信服务商与费用。
- **账本**：复式账；每笔资金事件对应借贷两侧，覆盖买家付款、微信或抖店手续费、退款、快递预充、工价、线材、结款；与微信、抖店账单对账。**待会计**确认科目与口径。
- **验证期**：订单从抖店导出 CSV 导入我们系统，我们系统是订单与运单号的主数据；面单手工在线寄件；运单号由 CSV 回填；不引入 ERP，量上来而 API 未就绪时再评估。

## 17. 第 6 轮决定与待写入设计的默认方案（2026-11-22）

### 17.1 用户已定
- **单位经济**：沿用既有价格经验，只验证不确定的数据；具体数字开发时由用户提供，不写进文档。
- **小程序首版商品**：只开放固定款，与抖店同款同价；成品专区另标价；一单一款。
- **小程序派单**：8:00–21:00 每小时整点派；夜里订单累积到次日 8:00；织女 1 小时内确认，超时按原规则改派；织女可设免打扰。
- **防派不出去**：下单前检查小程序池剩余容量（沿用"剩余工时 70%"算法）；为 0 显示"暂时售罄"，可预约到货提醒。
- **招募闸门**：`recruitGate`：近 4 周每位织女周均单量低于阈值则暂停新名额；阈值待数据。
- **准入漏斗**：完整四轮（作品照与小测验 → 指定款试做 → 样品寄回入库验收 → 首单），不放松；漏斗要单独设计：判定标准、复核人、驳回话术、样品运费补贴、吞吐量与招募闸门的协调。
- **买家客服**：小程序内微信客服消息 + 订单页"申请售后"；退款由运营审核后原路退回。
- **运营人力**：由用户自己决定；系统设计只维护 `06-人力成本节点台账.md` 并提示可自动化的节点。
- **质量退款**：待定（需要更多信息）；补充前不扣款。

### 17.2 我提出的默认方案（`建议`，未经你确认，可直接改）
1. **风控与反作弊**：成品照与封签照做图像指纹，跨单、跨织女重复即标记人工复核；照片读取并保留拍摄时间与设备信息；线材申领按单据额度与周频次校验，异常额度触发复核；志愿者审核每人每天上限、同一织女作品不重复分给同一志愿者、定期用标准样品校准；一人多号用手机号、微信、银行卡实名去重。
2. **物流异常责任**：织女不寄或超期不寄，按超期规则处理；运输丢损：平台先向买家赔付，是否购保价与向织女或快递公司追偿待定（需要你判断、咨询函未问）；取件失败自动重约 2 次后进待处理。
3. **现金流**：每周计算"预计垫付总额"（运费预充余额 + 待退款 + 待结款与未到账货款之差），设下限提醒；小程序货款先进商户号，结款前停留的时间要写进律师意见（咨询函第 1 题）。
4. **款式供给管线**：阶段 1 的款式只来自自有形象与自编图解；每个新款上架前必须有标准工时、工价、色号清单、图解审核、阶段 0 或熟人试做；上架节奏按图解产出能力定，不由订单驱动。
5. **测试与上线**：抖店禁止自买，抖店订单链路用真实订单与历史 CSV 样本测试；小程序用微信支付沙箱与真实小额支付（自己买、自己退）；单独测试环境，灰度先放熟人织女与社群老玩家；上线前演练一次"全部回滚"。
6. **小程序合规**：备案、隐私协议、图片内容安全审核、实名接口，列入开发前置清单；备案要求与时长**待核实**。

### 17.3 买家小程序最小功能清单
商品列表与详情（固定款、颜色、交期说明、成品专区）→ 下单与地址 → 微信支付 → 订单状态（待制作、制作中、已寄出、已签收）→ 物流查询 → 申请售后（订单页）→ 客服消息 → 到货提醒。定价与库存规则见 17.1。

### 17.4 对 §11 的修订（技术结构）
- **仓库**：`mp` 拆为 `mp-buyer` 与 `mp-weaver` 两个小程序，共用 `cloud`、`shared`、`admin`；包名前缀仍用 `@wxtz/*`。
- **新增集合**：`buyers`（openid、手机号、收货地址引用）、`products`（小程序商品，引用 `styles`）、`payments`、`refunds`、`notifications`、`tickets`、`volunteers`、`volunteerVotes`、`recruitFunnel`（织女准入各轮状态与评分）、`ledgerAccounts`（复式账科目）。
- **`users` 增加**：`pool`、`poolRank`、`cityQuotaKey`、`verifyLevel`、`funnelStage`。
- **`orderPackages.channel`**：`douyin_online` 或 `mp_wechat`；两条线共用同一状态机，退款来源不同：抖店靠 CSV（后续 API）回导，小程序靠微信支付回调与客服消息。
- **`config.recruitGate`**、`config.dispatchWindow`（8–21 点整点）、`config.capacityRule`（剩余工时 70%）。

## 18. 第 7 轮开发前细节定稿与主体策略（2026-11-24）

### 18.1 主体与抖店过渡策略 `定`
- **先用个体户开跑，有量后再迁移公司主体**：因个体户明确不能开通抖音开放平台，个体户阶段抖店直播池用**服务市场打单 ERP**（首选 `service_id=50` 中通吉快递管家 / `service_id=10` 快递100 快递管家，免电子面单账号、上门取件代打面单）过渡；小程序池直接走微信支付 + 快递100 API 全自动，不受抖音限制。
- **防迁移断链设计**：`users._id` 统一使用平台内部 `userId`（`usr_<id>`）+ `phone` 唯一索引，与两端 `openid` 解耦；微信支付商户号与密钥走独立配置，确保将来个体户迁有限公司时老用户凭手机号无痛衔接历史订单、信用分与线材池余额。

### 18.2 业务与风控细节定稿（10 项全定）`定`
1. **质量退款**：经核实确属织女质量问题需退买家全款时，**该单工价不结，但不倒扣织女其他钱**（扣信用分，累计多次暂停接单），平台兜底差额。
2. **小程序买家取消**：**派单前（织女未接单）直接秒退**；织女接单开工后走人工审核，固定款由织女继续做完照结工价，成品转入**成品余货**在小程序现货区销售。
3. **快递丢件/破损**：织女按标准交寄后发生运输丢损，**平台兜底赔买家 + 照常给织女结工价**，平台统一向快递公司理赔（高单价款勾选保价）。
4. **小程序预计交期**：固定款商品页统一展示稳妥区间（如“**下单后 3–5 天内发出**”），成品余货专区标“**48 小时内发**”。
5. **试做样品邮费与 200 元履约保证金（2026-11-24 更新定稿）**：试做样品邮费**织女自理、不报销**；新增 **200 元合作履约保证金**筛选门槛——在**通过照片作品审查后**即明确告知织女，接下来将考察指定作品的钩织能力，考察通过后须缴付 200 元保证金方可正式通过审核并开始接单（法律定性与退出全额退还条款纳入律师 L6 审定）。
6. **准入漏斗重提次数**：作品照/小测验最多重提 **2 次**；试做样品允许修改重寄 **1 次**；仍不通过进入 **30 天冷却期**。
7. **志愿者来源与上线时点（重要修正）**：**志愿者主要来源是粉丝（而非织女）**；志愿者审核功能必须在**正式运行前即开发就绪**，正式运行时即可招募粉丝志愿者协助审核作品照/试做照与日常成品照。因粉丝天然使用买家端，志愿者审核入口优先挂载在 `mp-buyer`（当 `users.roles` 含 `volunteer` 时展示），与 `userId` 统一打通，并保持匿名、回避同织女与标准样品校准机制。
8. **线材申领门槛**：**满 3 团起发**，或按“单款补色材料包”整包申领。
9. **双端账号互通**：允许同一人既当织女又当买家，通过内部 `userId` + 手机号打通；**派单引擎硬校验拦截自买自接**（买家 `userId !== assignedWeaverId`）。
10. **启动节奏**：**两条线并行**——立即用 3–5 位熟人织女在抖店（在线寄件 / 中通吉 ERP）跑真实订单验证手艺、工时与运费，同时开发小程序池（`mp-buyer` + `mp-weaver` + 快递100）。
